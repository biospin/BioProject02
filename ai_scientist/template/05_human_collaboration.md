# 05 — 다연구자 협업 구조 (원칙)

하네스는 진공에서 돌지 않는다. 사람들이 각자의 역할·검수 짝·작업 환경을 갖고 그 위에서 협업한다.

## (A) 1인 1역할 — 사람 역할과 에이전트 벤치를 대응시킨다

`{{TEAM_TABLE}}` 을 채우되, **각 사람이 어떤 워크스페이스와 어떤 에이전트 벤치에 대응하는지**까지 적는다.

| 필요한 것 | 왜 |
|---|---|
| 리더 `{{LEADER}}` | 스코프 확장·기준 변경을 **승인**한다 |
| 검수 총괄 `{{CRITIC_LEAD}}` | 판정과 최종 상태를 **owns** 한다 |
| 역할별 담당 | 산출물의 **owner**가 명확해야 owner≠reviewer가 성립한다 |

> 역할 겸임은 괜찮지만 **owner와 reviewer의 겸임은 안 된다.**

## (B) 작업 흐름 — 트래커에서 CLI까지

```
{{TRACKER}} 이슈 할당
    └→ {{NOTIFY_BOT}} 이 감지 → {{CHANNELS}} 로 알림
          └→ 담당자가 CLI 도구로 실제 작업
                └→ 커밋(이슈 번호 포함) → PR
                      └→ 트래커 상태 자동 갱신
```

**역할 구분을 흐리지 않는다:**
- **알림 봇** — 모니터링·알림 전용. **코드를 쓰지 않는다**
- **CLI 도구** — 사람이 직접 구동하는 구현 도구. 도구 선택은 각자 자유이되 **출력 스키마는 통일**한다

**브랜치·커밋 규약**을 정한다: `<type>/<이슈번호>-<사용자>-<설명>`, 커밋 메시지에 이슈 번호 포함(자동 연동).

> ⚠️ **트래커 조회 시 코멘트를 반드시 포함한다.** 대부분의 트래커는 기본 응답에 코멘트를 **빼고** 준다.
> 티켓의 실제 상태(승인·결정·지적)는 대개 **본문이 아니라 최신 코멘트**에 있다. 목록 조회 결과에도 코멘트가 없으므로, **실제로 손댈 티켓은 개별로 한 번 더** 조회한다.

## (C) 교차검수 — owner ≠ reviewer

**자기 결과를 자기가 검수하지 않는다.** `{{CROSS_REVIEW_MAP}}`(작성자 → 리뷰어)을 정하고, **같은 매핑을 자동 리뷰 루프에도 주입**한다. 사람 규칙과 AI 자동화가 같은 규칙을 공유해야 한다.

### 도메인 sub-check 선정규칙 — ⚠️ 고정 배정으로 쓰지 않는다

우선순위대로 적용하며 **1번이 2번을 이긴다:**

1. **해당 산출물·검증 대상 코드의 owner가 아닌 사람** — 제약이지 권고가 아니다
2. 도메인 기본 후보 — **후보 목록이고 고정 배정이 아니다**
3. 후보가 전부 owner면 → **리더가 다른 멤버를 케이스별로 지정**한다

> **왜 규칙으로 써야 하나:** 역할표에 "sub-check는 A/B가 담당"이라고 **고정으로** 적어두면, A가 산출물 owner이고 B가 검증 대상 코드의 owner인 순간 **문자대로 따르는 것이 규율 위반**이 된다. 실제로 일어난다([APPENDIX](APPENDIX_CASE_BIOP02.md)).
>
> **담당이 헷갈리면 역할표가 아니라 "이 산출물을 누가 만들었나"를 먼저 본다.**

## (D) 공유 인프라 규약 — 협업이 조용히 깨지지 않게

여러 사람이 **격리된 환경**에서 일하면 "내 쪽에선 보이는데 남은 못 보는" 실패가 생긴다. 다음을 **명시**한다:

- **`{{SHARED_VOLUME}}` 만이 공유 경로다.** 개인 홈은 대개 공유되지 않는다 — 권한을 열어도 **마운트 자체가 없으면** 안 보인다
- 공유 대상(중간 산출물·인덱스·분할·라벨)은 **공유 경로에 실파일로** 둔다. 개인 경로로의 심링크 금지
- 참조 경로는 **절대경로**로 쓴다
- 폴더·파일 네이밍 규약을 정한다 (버전 접미사 포함)
- 공유 폴더는 **그룹 상속 설정**(setgid 등)으로 만들어 권한이 자동 상속되게 한다
- `{{COMPUTE}}` 예약 규칙 — 사용 전 채널에 공지
- 영구 보존 대상과 삭제 대상을 구분한다. **삭제 정책이 재작업을 유발할 수 있으므로**, 디스크 부족 시 자동 삭제가 아니라 **정지 + 사람 판단**을 기본으로 한다

## (E) 상태 핸드오프 — 세션·사람 간 인수인계

`{{HANDOFF_FILES}}` 를 정하고 **목적을 구분**한다:

| 파일 | 목적 |
|---|---|
| 핸드오프 | **다음 사람이 이어받을 상태** |
| 세션 로그 | **그날 한 일의 날짜별 기록** (역시간순) |
| TODO | 남은 일 |

**규칙 2개:**
- **핸드오프를 갱신할 때 세션 로그도 같은 턴에 쓴다.** 누락 방지는 이 규칙으로 하지, 나중의 의지로 하지 않는다
- **개인 로그의 durability를 확보한다.** 로컬 디스크는 유실될 수 있으므로 공유 경로에 백업한다. 팀 공유 기록은 트래커·위키·PR 본문·레지스트리가 담당한다

> ⚠️ **세션 로그·기억은 상태의 근거가 아니다.** 상태를 인용할 땐 **기록 id 또는 `파일:줄`** 을 밝힌다.

### 한 층 더 — 수명이 다른 두 종류의 기록

핸드오프 3종이 **"지금 상태"** 를 넘긴다면, 별도의 기억 저장소는 **"세션이 바뀌어도 다시 배우지 않아야 할 사실"** 을 넘긴다. 섞으면 둘 다 못 쓴다.

| | 수명 | 담는 것 |
|---|---|---|
| 핸드오프 · 세션로그 · TODO | 며칠~몇 주 | 지금 막힌 것, 어제 한 일 |
| **`{{MEMORY_STORE}}`** | 프로젝트 내내 | 사람의 작업 방식·선호, 반복 확인된 운영 사실, 외부 자원 위치 |

**한 항목 = 한 파일 = 한 사실**로 두고 색인을 둔다. 다음 세션이 **먼저 읽는** 자리이기 때문이다.
넣을 가치가 있는 것은 **반복해서 대가를 치른 사실**이다(예: *"상태를 판단하기 전에 반드시 원격을 먼저 당긴다"*).

> ⚠️ **기억도 낡는다.** 기록 시점의 사실이므로, **파일·명령·플래그를 지목하는 항목은 쓰기 전에 아직 존재하는지 확인**한다.
> 리포에 없는 것을 "있다"고 기억하는 순간, 그 기억은 보호가 아니라 **오정보**가 된다.

## (F) 세션-간 **작업** 규율 — 파일이 아니라 행동

(E)가 *무엇을 남기나*(파일 층)라면 이 절은 *세션을 열고 닫을 때 무엇을 하나*(행동 층)다.
**둘은 짝이다** — 파일만 있고 규율이 없으면 **쓰긴 쓰는데 안 읽고, 읽어도 일부만 본다.**

> ⚠️ 이 규율은 **도구에 묶이지 않는다.** 어떤 CLI를 쓰든, 슬래시커맨드로 자동화하든 수동 체크리스트로 하든 상관없다.
> **통일하는 것은 도구가 아니라 규율이다** — 도구는 각자 몫으로 두고 A/B/C만 공통으로 지킨다.

### A. 착수 — 전수 스캔 (부분 스캔 금지)

**"내 할 일" = 배정 + 댓글/텍스트 멘션 + 신규 항목**, 셋 다 본다.
아래 3관문을 통과하기 전엔 **"할 일 없음"을 선언하지 않는다.**

| 관문 | 무엇을 막나 |
|---|---|
| **A** | 마지막 댓글이 *타인*이면 **말미**를 읽는다 — 본문이 진행보고여도 **끝에 요청이 박혀 있다**(신호: *부탁 · 확인 후 · 주시면 · 병합 · 결정 · 물음표*) |
| **B** | 마지막 댓글이 *본인*이어도 **"공이 넘어갔다"고 단정하지 않는다** — 상태기록에 열린 항목이 없는지 교차확인 |
| **C** | **전 댓글 전수 스캔** — 내 할 일이 *오래된* 댓글에 박혀 있고 그 뒤로 남들이 진행보고를 쌓아 **마지막이 아닌** 경우가 많다 |

> **목록 조회에는 댓글이 없다**(→ [INTEGRATIONS §2](INTEGRATIONS.md)). 실제로 손댈 항목은 **개별로 댓글까지** 다시 연다.
> 관문 C가 특히 잊힌다 — "마지막 댓글만 보면 된다"는 직관이 틀리는 자리다.

### B. 마무리 — 4구역 반영

작업이 끝나면 **그 자리에서** 네 곳 전부에 반영한다. *"반영하겠다"는 말이 아니라 **그 턴에 실제로**.*

| 구역 | 무엇을 |
|---|---|
| **git** | 미커밋 산출물 커밋·푸시. 리뷰 필요분은 PR + 리뷰어 지정(**Owner ≠ Reviewer**) |
| **트래커** | 본문·댓글·상태. **완료 게이트 충족 시에만** 완료 전환(게이트 우회 금지) |
| **상태기록** | 개인 상세 로그 + "다음이 이어받을" 인계 메모 |
| **`{{MEMORY_STORE}}`** | 인프라·도구 문제를 풀었으면 기록 — **재시작 후 같은 디버깅 반복 방지** |

> 흔한 누락이 정확히 이 네 칸에서 난다: *코드만 짜고 커밋 안 함 / 분석만 하고 트래커 미기록 / 핸드오프만 쓰고 세션로그 빠뜨림.*

### C. 개인기록 ↔ 팀기록 분리 — 이 층의 핵심 경계

- **개인 로그는 버전관리에 올리지 않는다.** 중간 상태·자기정정·사람 메모라, 팀 영구 히스토리에 넣으면 신호는 안 늘고 **노이즈와 오독**만 는다 — *나중에 뒤집은 잠정 판단이 팀엔 확정처럼 읽힌다.*
- **팀 기록 = 큐레이트 채널**(트래커·위키·PR 본문·레지스트리). "공유 상태"가 필요하면 개인 로그를 노출하는 게 아니라 **이 채널들을 최신으로 유지**한다 — 그게 §B가 하는 일이다.
- **durability는 백업으로** — 개인 로그가 사라지는 것과 팀에 공개하는 것은 다른 문제다.

> **A와 B는 같은 실패의 앞뒤다** — *부분만 보고 "됐다/없다"를 단정하는 것.*
> A는 착수 시점의 단정(**"할 일 없다"**)을, B는 종료 시점의 단정(**"반영 다 했다"**)을 막는다.

## 채널

`{{CHANNELS}}` 를 목적별로 분리한다 — 공지 / 작업 진행 / **결과 공유(검수 통과 후만)** / 자원·장애.

> **결과 공유 채널은 검수 통과 후에만 쓴다.** 이 규칙이 없으면 검수 게이트가 사실상 사라진다.
