# 01 — 2-레이어 아키텍처 (원칙)

## 원칙

AI Scientist를 **하나의 거대한 자율 에이전트로 만들지 않는다.** 책임이 다른 두 레이어를 분리하고, 위 레이어가 아래 레이어의 산출물을 **파일로** 소비한다.

```
┌──────────────────────────────────────────────────────────────┐
│  레이어 B — 논문 생산 하네스  (도메인 무관 · 재사용)          │
│  문헌·기획 → 집필·그림 → 심사 → 발표                          │
│  입구 = 오케스트레이터 Skill (메인 루프가 실행)               │
└───────────────────────────▲──────────────────────────────────┘
                            │ 결과 파일 + 요약을 소비
                            │ (도메인 슬롯 {{DOMAIN_AGENT}} 가 다리)
┌───────────────────────────┴──────────────────────────────────┐
│  레이어 A — 도메인 분석 파이프라인  (프로젝트 고유)           │
│  {{PIPELINE_STAGES}}                                          │
│  결과물 = {{EXPERIMENT_DIR}} 의 {{REQUIRED_ARTIFACTS}}        │
└──────────────────────────────────────────────────────────────┘
```

## 왜 나누나

| 이유 | 설명 |
|---|---|
| **재사용성** | 레이어 B는 도메인과 무관한 **연결조직**이다. 다른 프로젝트에 그대로 옮겨 붙는다. |
| **관심사 분리** | A = "숫자가 맞나"(누수·기준선·재현성). B = "그 숫자를 정직하게 쓰나". **게이트가 그 경계에 놓인다.** |
| **성숙도 흡수** | 집필-단계 산출물이 아직 없어도 B를 미리 배선해 둘 수 있다. 없는 것은 `<FILL>`로 **없다고 표시**한다. |

> **핵심 설계 규칙: 도메인 특수성은 슬롯 하나(`{{DOMAIN_AGENT}}`)에 격리한다.**
> 도메인 지식이 여러 에이전트에 흩어지면 레이어 B의 재사용성이 사라진다. 슬롯 자체는 단일 스크립트가 아니라 역할 워크스페이스들의 **대표**여도 된다.

## 레이어 A — 의존성 체인

역할 사이의 **의존 순서를 명시**한다. 앞 단계 산출물이 뒤 단계의 착수 조건이다.

```
{{PIPELINE_STAGES}}
        └→ 검수 → 검수 리포트 → (통과 시) 등록·공유
```

**모든 실험은 아티팩트로 봉인한다** — `{{REQUIRED_ARTIFACTS}}` + `{{METRIC_FIELDS}}`(커밋 해시 포함).
이 강제 계약이 *"실험을 실제로 수행했다"* 의 재현 가능한 증거다. 목록이 짧아도 좋지만 **비어 있으면 안 된다.**

## 레이어 B — 표준 경로

```
기획·근거   →  분석·검증  →  집필·그림  →  내부 적대검수
                                    ↑              │ (수정)
                                    └──────────────┘
   →  🔒 검증 게이트 ① (커밋 전)
   →  (선택) 외부 리뷰 · 격리
                                    ↑              │ (수정)
                                    └──────────────┘
   →  🔒 검증 게이트 ② (공개 직전)  →  발표
```

## 게이트 배치 — 이 하네스에서 가장 중요한 결정

| 게이트 | 시점 | 무엇을 |
|---|---|---|
| 🔒 **검증 게이트 ①** | 커밋 전 | 헤드라인 숫자를 결과 파일에서 **결정론적으로 재계산**해 대조. 실패하면 **멈추고 사람에게 보고**, 커밋·발행 금지 |
| 🔒 **검증 게이트 ②** | 공개 직전 | 본문 숫자 ↔ 결과 파일 재대조 + 그림·표·부록 동봉 확인 |
| 🔒 **공개 게이트** | 공개 전 | 저자·소속·순서·교신·라이선스·자원 제공처 확정 |

### 순서가 왜 이런가

> **게이트가 외부 리뷰보다 **앞**에 온다.** 원본 하네스 규칙: *"critic + gate **FIRST**, then reviewer — reviewer assumes pre-submission QA is done."*
> 요지는 하나다 — **검증되지 않은 숫자를 리뷰에 보내지 않는다.**

그리고 게이트는 **1개가 아니라 2개**다. 리뷰를 반영하면 본문이 바뀌므로 **공개 전에 한 번 더** 돈다.

### ⚠️ 처음부터 정할 것 — 게이트 ①의 실행 명령

`{{VERIFY_GATE_1_CMD}}` 를 **실물 명령으로** 만든다. 두 가지를 혼동하지 않는다:

| | 하는 일 | 게이트 ①인가 |
|---|---|---|
| 문서 규칙 검사 | 금지어·필수 필드·주장 수준 표기 확인 | ❌ 아니다 |
| **수치 재계산** | 결과 파일에서 헤드라인을 다시 계산해 대조 | ✅ 이것이다 |

이 자리를 비워두면 "검증했다"가 **사람의 기억**에 의존하게 된다. (BIOP02가 실제로 치른 비용 → [APPENDIX](APPENDIX_CASE_BIOP02.md))

## ⚠️ 처음부터 정할 것 — 게이트 이후 "수정"의 권한

게이트 ① 이후의 수정 단계는 **검증을 무효화할 수 있는 유일한 지점**이다. 집필 에이전트가 쓰기 권한을 가지면 원고를 통째로 다시 쓸 수 있고, 그때 게이트가 확인한 숫자·인용이 **조용히 바뀌어도 에러가 나지 않는다.**

- 게이트 ②와 숫자 드리프트 검사는 **사후 탐지**이지 사전 차단이 아니다
